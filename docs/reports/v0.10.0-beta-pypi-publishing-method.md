# QA-Z v0.10.0-beta PyPI Publishing Method Decision

Status: decision prep only. No upload in this PR.

## Options

| Method | Approval requirements | Credential boundaries | GitHub permission implications |
| --- | --- | --- | --- |
| Manual PyPI API token | Release owner must approve production PyPI publish, package version, exact SHA, and operator. | Token must be handled out of band. Do not write it into docs, logs, env snapshots, or repo files. Credential presence is not approval. | No new workflow permissions are required, but the human operator becomes the audit boundary. |
| PyPI Trusted Publishing via GitHub Actions | Release owner must approve production PyPI publish, package version, exact SHA, and a dedicated workflow change. PyPI project must trust the GitHub repository/workflow/environment. | No long-lived PyPI token is stored in the repository. Publishing authority is scoped through PyPI trust configuration and GitHub environment protection. | Requires a narrowly scoped workflow with `id-token: write` and read-only repository contents unless the workflow has another justified need. Environment reviewers should gate the publish job. |

## Recommended path

Recommended path: PyPI Trusted Publishing via GitHub Actions.

Reason: it avoids a long-lived manual PyPI API token in local operator flows,
keeps the production PyPI publish behind a reviewable workflow/environment gate,
and provides a clearer audit trail for the exact commit, package version, and
registry event.

## Boundary

This decision does not create or change the publishing workflow. It does not
grant GitHub permissions, configure PyPI trust, create environments, or perform
registry mutation. The production PyPI publish remains blocked until a separate
owner-approved PR and execution packet complete the required gates.
