# v0.14 Repair -> Verify Workflow

Date: 2026-05-27

## Purpose

Make the failed-guard to repair-prompt to verify loop a first-class QA-Z product
workflow. The user should be able to read the repair handoff, apply a focused
fix outside QA-Z, and run one verify command that reports whether the repair
improved the evidence.

## What Changed

- Added `qa-z verify --from-run <run>` as the first-class baseline alias.
- Made `qa-z verify --from-run latest` rerun candidate fast evidence and
  comparable deep evidence automatically when no explicit candidate run is
  provided.
- Kept `--baseline-run` and `--candidate-run` compatibility for existing
  scripts with prebuilt candidate runs.
- Added artifact and `next_actions` pointers to verify CLI JSON output.
- Improved human verify output with the verdict, before/after blocker delta,
  artifact paths, and next commands.
- Kept rerun deep evidence comparable: candidate deep checks run only when the
  baseline has deep evidence.
- Added explicit forbidden shortcuts and the follow-up verify command to Codex
  repair handoffs.
- Updated the auth-bug demo and installed-package smoke path to copy the fixed
  implementation and verify `improved`.

## Product Value

The primary QA-Z loop now matches the user story:

```bash
qa-z guard --from-run latest --adapter codex
qa-z repair-prompt --from-run latest --adapter codex
# apply the repair outside QA-Z
qa-z verify --from-run latest
```

Users no longer need to manually create a candidate run for the common local
repair path. They still can use explicit baseline/candidate mode for CI or
scripted evidence.

## Demo Evidence

The packaged auth-bug demo includes `app/auth.fixed.py` and the deterministic
verify command:

```bash
qa-z demo auth-bug
cd .qa-z/demo/auth-bug
cp app/auth.fixed.py app/auth.py
qa-z verify --from-run latest --config qa-z.demo.yaml
```

Expected result: `QA-Z Verify: improved` and
`.qa-z/runs/candidate/verify/report.md`.
