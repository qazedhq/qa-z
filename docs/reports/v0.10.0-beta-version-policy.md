# QA-Z v0.10.0-beta Version Policy

Policy date: 2026-05-16
Decision type: release-owner version policy, not release execution.

This policy does not release `v0.10.0-beta`. This metadata-only PR changes
`pyproject.toml` from `0.9.8a0` to `0.10.0b0`, but it does not create a tag,
create a GitHub Release, publish a package, deploy, or prove package-registry
availability. It records the owner-approved version choice before a separate
approved production PyPI execution packet can run.

- `VERSION_METADATA_CHANGE_APPROVED=true`
- `TARGET_PACKAGE_VERSION=0.10.0b0`
- `SELECTED_RELEASE_PATH=production PyPI beta preparation`
- `PYPI_UPLOAD_ALLOWED=false`
- `TESTPYPI_UPLOAD_ALLOWED=false`
- `REGISTRY_UPLOAD_ALLOWED=false`

`docs/reports/v0.10.0-beta-release-execution-checklist.md`. The checklist does
not execute release actions, and release execution remains `NO-GO`.

Rollback/yank policy:

Package publish path decision:

## Tag Name vs Package Metadata

GitHub tag names and Python package metadata versions are related but not
identical.

- `v0.10.0-beta` is a human-facing GitHub release/tag target.
- `0.10.0b0` is the current PEP 440 package metadata for production PyPI beta
  preparation after this PR.
- `0.9.8a0` is the historical TestPyPI rehearsal metadata.
- A GitHub prerelease-only path can choose a tag without publishing a package,
  but any attached package artifacts must still avoid confusing beta claims.
- A TestPyPI or PyPI path must choose a PEP 440 package metadata version before
  upload.

## Approval Requirements

Before any tag, GitHub Release, package publish, or deploy, the release owner
must record:

- `RELEASE_EXECUTION_APPROVED=true`
- `PACKAGE_PUBLISH_ALLOWED=true` for any registry upload
- release owner
- release type
- target tag when a GitHub release/tag is involved
- target package metadata version when package artifacts or registry upload are
  involved
- target registry for TestPyPI, PyPI, npm, GitHub Packages, or another registry
- exact release SHA
- remote CI proof SHA; historical proof is recorded in
  `docs/reports/v0.10.0-beta-exact-sha-proof.md`, while final proof must follow
  `docs/reports/v0.10.0-beta-final-sha-proof-protocol.md`
- public raw proof SHA; historical proof is recorded in
  `docs/reports/v0.10.0-beta-exact-sha-proof.md`, while final proof must follow
  `docs/reports/v0.10.0-beta-final-sha-proof-protocol.md`
- rollback/yank policy
- external proof links

Credential presence is not approval.

## Blocked Actions

These actions remain blocked by this policy unless a later approved execution
packet satisfies the requirements above:

- changing `pyproject.toml` version without release-owner approval;
- creating a tag;
- creating a GitHub Release;
- publishing to PyPI, TestPyPI, npm, GitHub Packages, or any package registry;
- running `twine upload`, `uv publish`, `npm publish`, or deploy commands;
- deploying a docs site or hosted demo;
- mutating GitHub settings;
- posting bot comments;
- calling live model APIs;
- claiming `twine`, `pipx`, or `uvx` smoke passed without fresh evidence;
- hiding the Next.js/PostCSS advisory blocker.
- treating PR-committed exact SHA proof as final release proof after the proof
  PR merges.

## Recommended Decision

Recommended decision: keep `v0.10.0-beta` planned, align package metadata to
`0.10.0b0`, and keep production PyPI blocked until a separate execution packet.

Before production PyPI conversion, the release owner must still choose:

- a release-owner advisory decision or a final proof packet after SHA freeze;
- a separate release execution packet with exact SHA proof, approvals,
  credentials, and rollback/yank policy.

## Future Execution Packet Requirements

A future execution packet must restate this policy and add the missing proof for
