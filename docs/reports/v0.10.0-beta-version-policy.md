# QA-Z v0.10.0-beta Version Policy

Policy date: 2026-05-16
Decision type: release-owner version policy, not release execution.

This policy does not release `v0.10.0-beta`. It does not change
`pyproject.toml`, create a tag, create a GitHub Release, publish a package,
deploy, or prove package-registry availability. It records the version choices
that a release owner must make before a separate approved release, rehearsal, or
metadata-only packet can run.

| Surface | Current truth | Status |
| --- | --- | --- |

| Current package metadata | `0.9.8a0` in `pyproject.toml`. | Current metadata |

## What Is Not Being Changed

- `pyproject.toml` remains at `version = "0.9.8a0"`.
- `0.10.0b0` is a candidate package metadata version, not current metadata.
- `v0.10.0-beta` remains planned, not released.
- `pipx install qa-z` and `uv tool install qa-z` are future PyPI-published
  install paths, not current live install claims.
- This policy does not authorize tag creation, GitHub Release creation, package
  publish, deploy, registry mutation, GitHub settings mutation, bot comments, or
  live model calls.

## Version Policy Options

| Option | When it fits | Package metadata effect | Release effect |
| --- | --- | --- | --- |
| Keep `0.9.8a0` | No release yet, local-only evidence, or GitHub source/tag install docs remain the active install path. | No change. | No release execution. |
| Bump to `0.10.0b0` | Release owner approves a beta package metadata PR before TestPyPI/PyPI publish or package artifacts that should identify as beta. | Separate approved PR changes `pyproject.toml` and updates tests/docs. | Still no publish/tag/release unless separately approved. |
| GitHub prerelease tag only | Release owner wants a GitHub prerelease without registry upload. | Not necessarily changed, but the tag and package metadata relationship must be explicit. | Requires tag/release approval and exact-SHA proof in a separate packet. |
| TestPyPI rehearsal only | Release owner wants local package smoke or no-upload rehearsal evidence. | No change unless a separate version PR is approved first. | No registry upload; `registry_upload_executed=false`. |
| TestPyPI publish | Release owner approves a TestPyPI upload. | Target package metadata version must be selected and PEP 440-compliant. | Separate approved upload packet required. |
| PyPI publish | Release owner approves the real public package. | Public package metadata version must be selected and PEP 440-compliant. | Separate approved production release packet required. |

## Tag Name vs Package Metadata

GitHub tag names and Python package metadata versions are related but not
identical.

- `v0.10.0-beta` is a human-facing GitHub release/tag target.
- `0.10.0b0` is the likely PEP 440 package metadata candidate for a first beta
  build.
- `0.9.8a0` is the current metadata in `pyproject.toml`.
- A GitHub prerelease-only path can choose a tag without publishing a package,
  but any attached package artifacts must still avoid confusing beta claims.
- A TestPyPI or PyPI path must choose a PEP 440 package metadata version before
  upload.

## Approval Requirements

Before any tag, GitHub Release, package publish, or deploy, the release owner
must record:

- `RELEASE_EXECUTION_APPROVED=true`
- `PACKAGE_PUBLISH_ALLOWED=true` for any registry upload
- release owner
- release type
- target tag when a GitHub release/tag is involved
- target package metadata version when package artifacts or registry upload are
  involved
- target registry for TestPyPI, PyPI, npm, GitHub Packages, or another registry
- exact release SHA
- remote CI proof SHA; historical proof is recorded in
  `docs/reports/v0.10.0-beta-exact-sha-proof.md`, while final proof must follow
  `docs/reports/v0.10.0-beta-final-sha-proof-protocol.md`
- public raw proof SHA; historical proof is recorded in
  `docs/reports/v0.10.0-beta-exact-sha-proof.md`, while final proof must follow
  `docs/reports/v0.10.0-beta-final-sha-proof-protocol.md`
- rollback/yank policy
- external proof links

Credential presence is not approval.

## Blocked Actions

These actions remain blocked by this policy unless a later approved execution
packet satisfies the requirements above:

- changing `pyproject.toml` version without release-owner approval;
- creating a tag;
- creating a GitHub Release;
- publishing to PyPI, TestPyPI, npm, GitHub Packages, or any package registry;
- running `twine upload`, `uv publish`, `npm publish`, or deploy commands;
- deploying a docs site or hosted demo;
- mutating GitHub settings;
- posting bot comments;
- calling live model APIs;
- claiming `twine`, `pipx`, or `uvx` smoke passed without fresh evidence;
- hiding the Next.js/PostCSS advisory blocker.
- treating PR-committed exact SHA proof as final release proof after the proof
  PR merges.

## Recommended Decision

Recommended decision: keep `v0.10.0-beta` planned and keep package metadata at
`0.9.8a0` until the release owner chooses either:

- a no-upload tool-equipped package smoke rehearsal;
- a separate version metadata PR, likely selecting `0.10.0b0` for beta package
  metadata; or
- a separate release execution packet with exact SHA proof, approvals,
  credentials, and rollback/yank policy.

## Future Execution Packet Requirements

A future execution packet must restate this policy and add the missing proof for
the selected path. At minimum, it must include the exact release SHA, chosen
release type, selected target tag, selected target package metadata version,
registry policy, approval fields, final SHA proof generated after
release-candidate SHA freeze, CI proof, public raw proof, package smoke results,
generated-artifact cleanup, rollback/yank policy, and explicit confirmation
that no unapproved tag, GitHub Release, package publish, deploy, bot comment,
settings mutation, or live model call occurred.
