# v0.19 PyPI Trusted Publishing Design

Date: 2026-05-27

Status: future/design-only. This design does not create secrets, configure PyPI
trust, mutate GitHub repository settings, or run a publish workflow.

Do not create secrets, configure PyPI trust, or mutate GitHub repository
settings from this design.

## Options

| Method | Approval boundary | Credential boundary | Audit shape |
| --- | --- | --- | --- |
| Manual PyPI API token | Release owner approves exact version, SHA, operator, and execution window. | Long-lived token is handled out of band. Credential presence is not approval. | Human operator and local shell become the audit boundary. |
| PyPI Trusted Publishing via GitHub Actions | Release owner approves exact version, SHA, workflow, and protected GitHub environment. | No long-lived PyPI token is stored in the repository. PyPI trusts a GitHub OIDC identity scoped to repository, workflow, and environment. | GitHub run, environment approval, OIDC exchange, and PyPI event form the audit path. |

## Recommendation

Recommended default: PyPI Trusted Publishing via GitHub Actions.

Manual token fallback: explicit fallback only.

Trusted Publishing is the default because it avoids a durable local PyPI token,
keeps production release authority inside a reviewable workflow, and lets the
publish job be gated by GitHub environment reviewers.

## Required GitHub Shape

- GitHub environment name: `pypi-production`.
- Required workflow permission: `id-token: write`.
- Required workflow permission: `contents: read`.
- Keep all other permissions absent unless a later execution packet justifies
  them.
- Require environment reviewers before the publish job can run.
- Require the package version and final SHA in the reviewed workflow inputs or
  dispatch payload.
- keep PyPI upload separate from normal CI by using a dedicated, manual,
  protected release workflow.

## Required PyPI Shape

The PyPI project must trust only the intended GitHub repository, workflow file,
environment, and package project. The trust relationship must be configured by
a release owner outside this repository change and proven in the execution
packet before upload.

## What Must Not Be Logged

Do not log credential values, token material, OIDC token payloads, or registry
responses containing secrets.

Do not log `.pypirc`, environment dumps, secret names with values, request
headers, or full trusted-publishing exchange payloads. It is acceptable to log
secret names, missing/present status, workflow run URL, final SHA, artifact
hashes, package filename, package version, and public package URL after a future
successful publish.

## Separation From Normal CI

Normal CI may build, test, lint, and run `twine check`, but it must not publish.
The production PyPI job should be a separate protected workflow or protected job
that starts only after release-owner approval. Pull request checks must never
obtain production PyPI publish authority.

## Explicit Non-Actions

- No PyPI trust was configured.
- No GitHub environment was created or changed.
- No GitHub repository setting was mutated.
- No secret was created, read, printed, or committed.
- No package upload command ran.
- No README install transition occurred.
