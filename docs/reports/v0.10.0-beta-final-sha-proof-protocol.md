# QA-Z v0.10.0-beta Final SHA Proof Protocol

Protocol date: 2026-05-17
Decision type: final SHA proof protocol, not release execution.

This protocol stops the recurring exact-SHA-proof PR loop. It defines when final
release proof must be generated, where it may be stored, and which release gates
remain separate from SHA proof.

## Purpose

The purpose of this protocol is to separate historical proof committed through
normal pull requests from final release proof generated at release execution
time.

Normal release-readiness PRs may document evidence, decisions, and blockers.
They must not be treated as final release proof when merging them changes the
candidate SHA that they describe.

This protocol does not release `v0.10.0-beta`.

Release execution checklist:
`docs/reports/v0.10.0-beta-release-execution-checklist.md`. The checklist does
not execute release actions, and release execution remains `NO-GO`.

## Why PR-committed Proof Becomes Historical

A proof committed to `main` changes `main` when the proof PR is merged.
Therefore, PR-committed exact SHA proof becomes historical after merge.

The current history shows the loop:

| Proof packet | What it proved | Why it became historical |
| --- | --- | --- |
| PR #66 | PR #65 baseline `865efa12fccc1976d6d9bf2cddec89bca6610f67` | PR #66 merged and moved `main` to `7ec919b8ed255e623c7b684d296d8256d82d16ca`. |
| PR #67 | PR #66 merge SHA `7ec919b8ed255e623c7b684d296d8256d82d16ca` | PR #67 merged and moved `main` to `31706c0c7843ecac0c6e1a401ac0e5b762e27bc5`. |

Creating another PR whose only purpose is to refresh main SHA proof repeats the
same loop. It creates useful historical evidence, but it cannot be the final
release-execution proof by itself.

## Historical Proof vs Final Release Proof

Historical proof is useful. It records what was true for a previous SHA, which
CI runs passed, which raw files were reachable, and which actions were not
performed.

Final release proof is different. Final proof must be generated after the
release-candidate SHA is frozen and before any approved tag, GitHub Release,
package publish, deploy, or version execution step runs.

Historical proof may live in repository docs. Final release proof must not rely
on a follow-up source PR whose merge changes the candidate SHA again.

## Release-candidate SHA Freeze

A release-candidate SHA is frozen only after:

- release-owner approval records the intended release or no-release path;
- the chosen candidate commit is selected;
- no source-changing release-readiness PR is expected before execution;
- package metadata/version decision is recorded;
- package-smoke, advisory, credential, and rollback/yank gates have explicit
  `PASS`, `BLOCKED`, `NOT RUN`, or `NO-GO` status;
- the release owner agrees that this SHA is the execution candidate.

Final proof must be generated after this freeze, which means final proof must be
generated after the release-candidate SHA is frozen. If `origin/main`, the
selected release-candidate branch, or the selected tag target moves after proof
generation, the proof is stale and must be regenerated for the newer SHA.

## Required Final Proof Fields

A final SHA proof packet must include:

- exact release-candidate SHA;
- source ref used for release execution;
- `CI` run ID, event, branch/ref, status, conclusion, and URL;
- `Public Raw Hygiene` run ID, event, branch/ref, status, conclusion, and URL;
- exact-SHA public raw accessibility for release-critical files;
- package smoke status, including `twine`, `pipx`, and `uvx`;
- Next.js/PostCSS advisory decision status and proof link;
- package metadata/version decision;
- registry credential state without printing credentials;
- rollback/yank policy;
- generated-artifact cleanup status;
- release-owner approval fields;
- explicit non-actions for any step not approved or not run;
- final freshness check showing the candidate SHA still matches the selected
  execution ref immediately before execution.

## Allowed Storage Locations

Allowed storage locations for final proof are:

- release execution packet generated after SHA freeze;
- release-candidate branch artifact that does not need to be merged back before
  execution;
- GitHub Actions artifact attached to the frozen candidate SHA;
- approved release notes attachment after release approval;
- local operator evidence bundle referenced from the release execution packet.

The storage choice must preserve the frozen SHA. Proof storage must not change
the candidate SHA.
If storing the proof changes the candidate SHA, that proof is historical, not
final.

## Disallowed Actions

This protocol does not authorize:

- creating tags;
- creating GitHub Releases;
- publishing packages;
- running `twine upload`;
- deploying;
- changing `pyproject.toml`;
- bumping version metadata;
- mutating GitHub settings;
- posting bot comments;
- calling live model APIs;
- committing generated artifacts;
- creating another PR whose only purpose is to refresh main SHA proof again.

## Release-owner Checklist

Before release execution, the release owner must confirm:

- `RELEASE_EXECUTION_APPROVED` is recorded for the selected action;
- `PACKAGE_PUBLISH_ALLOWED` is recorded before any package upload;
- target tag is selected when a tag or GitHub Release is involved;
- target package metadata version is selected when package artifacts or
  registry upload are involved;
- final SHA proof was generated after release-candidate SHA freeze;
- final proof still matches the selected execution ref;
- `twine`, `pipx`, and `uvx` smoke statuses are recorded;
- Next.js/PostCSS advisory status is resolved, deferred, or accepted by an
  explicit release-owner decision;
- registry credential state is known without exposing credentials;
- rollback/yank policy is selected;
- no unapproved tag, GitHub Release, package publish, deploy, version bump,
  GitHub settings mutation, bot comment, or live model call occurred.
