# v0.19 PyPI Rollback/Yank Execution Playbook

Date: 2026-05-27

Status: execution playbook only. No package yank, delete, upload, release,
deploy, tag, or incident action occurred in v0.19.

PyPI production is distinct from TestPyPI. TestPyPI rehearsal proof does not
authorize production PyPI publish, production yanking, production deletion, or
README install transition.

## When To Yank

Yank should be considered when to yank a production PyPI file or release only
after all of these are true:

- a production PyPI package version exists;
- the version is wrong, unsafe, broken, or materially misleading;
- users should stop selecting it by default;
- a release owner and incident owner approve the action;
- the PyPI yanking policy has been checked at execution time;
- a replacement version, advisory, or user communication plan exists.

## When Not To Delete

Do not delete a production PyPI release as the default response.

Prefer yanking, replacement through a new version, or an advisory unless the
release owner confirms deletion is permitted, low risk, and documented under
current PyPI policy. Deletion can break reproducibility and downstream
consumers. A local git revert or `dist/` cleanup is not registry rollback proof.

## Who Approves

Required approvers:

- release owner for package/version action;
- incident owner for communication and user-impact handling;
- registry owner or PyPI project maintainer for permissions;
- security owner when the incident includes vulnerability or credential risk.

## Evidence Required

Before any production PyPI yank/delete/incident action, record:

- package name and version;
- production PyPI URL;
- exact source SHA and release workflow run;
- artifact hashes;
- install smoke result and failure mode;
- owner approval;
- official PyPI policy checked at execution time;
- selected response: yank, keep, replace with new version, advisory, or delete;
- communication target and message;
- post-action proof URL/API result;
- validation rerun after the response.

## Post-Incident Documentation

Document post-incident facts in a new report rather than editing historical
proof to look successful. Include timeline, affected users, root cause, action
taken, proof links, follow-up tests, and any README or release-note correction.

## TestPyPI Boundary

TestPyPI can be used for rehearsal and packaging proof, but TestPyPI actions do
not prove production PyPI state. Keep TestPyPI package URLs, credentials,
approvals, and smoke results separate from production PyPI package URLs,
credentials, approvals, and smoke results.
